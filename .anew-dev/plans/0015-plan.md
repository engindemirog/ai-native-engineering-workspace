## Files to change or add
- `scripts/upgrade` (new, POSIX sh): run as the new release's own copy —
  `<new>/scripts/upgrade <base-dir> <project>` (A-1), as `scripts/adopt` runs from its source:
  - the set: `scripts/adopt`'s files and folders but `.anew-version` (the agent writes it last);
    `AGENTS.md` and the `docs/` files bootstrap rewrote fall under the rule below like any other
    (Risk 5); plus each installed adapter's files, mapped
    as `scripts/init` places them (`CLAUDE.md`, `.claude/`; `.github/copilot-instructions.md`,
    `.github/{prompts,agents,instructions}/`; `.cursor/{rules,commands}/`; `.agents/skills/`);
  - per path, base `b`, new `n`, project `p`: `p` = `n` → `same`; `p` = `b` (or absent in both
    `p` and `b`) → `replaced` / `added` / `removed`; else `n` = `b` → `kept` (the project's change,
    nothing new); else → `merge`;
  - one line per path that is not `same`; a summary line; nothing committed; the mode of a new
    script set executable, and the `git add --chmod=+x` line as adopt prints it;
  - refusals: `<project>` not configured (AGENTS.md still the template's), a dirty working tree,
    a `<base-dir>` or the script's own release that is not an unconfigured ANEW release, or a
    base whose `.anew-version` differs from the project's.
  - Idempotent: run again, the files it wrote are `same`; the `merge` list is unchanged.
- `scripts/selftest`: a `scripts/upgrade` section (fixtures: a base and a new release built from

## Risks & open questions
1. **AC-6 needs v1.32 published**: the screen offers the latest release, and v1.32 is the first
   with `scripts/upgrade`. Recommendation: as 0013's AC-5 — the integration test proves the path
   on fixture releases before the merge; the human runs AC-6 on the published v1.32 right after
   the release; a failure there is fixed as v1.32.1.
2. **A-1 (proposed with this plan): the script's arguments.** A project on v1.31 has no
   `scripts/upgrade`; the new release's copy must run. Recommendation: `<new>/scripts/upgrade
   <base-dir> <project>` (the spec's Requirement 3 names `<base-dir> <new-dir>` run in the
   project) — the same two inputs, the way adopt runs.
3. **A-2 (proposed with this plan): the CHANGELOG headings shown after Fetch.** Before it, only the
   two tags and the compare link are known without a further download. Recommendation: the
   section names base → new and the compare link; the headings appear once the new release is
   fetched (Requirement 1).
4. **The adapter mapping lives in two scripts** (init, upgrade). Recommendation: selftest installs
   every adapter with `init` into a fixture and checks upgrade reaches each installed file.
5. **A file bootstrap rewrote** (most of `docs/`) differs from the base: with a change in the new
   release it is `merge`, otherwise `kept` — the agent sees only what changed upstream.
6. **The project's branch to start from:** `chore/anew-<tag>` is created from the current branch;
   the confirmation names it. A dirty tree is refused before anything is fetched.
7. **Environment:** low memory: one selftest or npm run at a time; selftest's own run from the
   screen takes minutes and is said so.
