# Spec 0005 — v1.24 is the first LTS line

- Status: Shipped
- Mode: lite (ANEW's own development)
- Plan: `.anew-dev/plans/0005-plan.md`
- Self-critique: done (G-1, G-2 folded in below)

## Intent
Four to five organizations asked for ANEW training. Releases moved from v1.21 to v1.24 in days:
good for development, bad for teaching — material written for one version is stale two weeks
later, and a team cannot tell which changes it must take. A frozen line gives trainers, trainees
and adopting teams one version to stand on while new work continues on `main`.

Today the line has nothing to stand on: the newest tag and GitHub release is v1.16, so v1.19–v1.24
cannot be checked out by name and every CHANGELOG `/compare/` link from v1.18 on is broken (G-1).

Success means a team can start from `v1.24.x`, knows that line takes fixes only and for how long,
can check out every released version by its tag, and a maintainer knows how a fix reaches the line.

Deliberately not done: changing any rule, script behavior or invariant; B-1…B-7 (each still needs
its own decision); training material; a second LTS policy for strict vs lite (one line covers both).

## Requirements
1. **Tags for every release.** v1.19, v1.20, v1.21, v1.22, v1.22.1, v1.23, v1.24 are tagged on
   the commit that shipped each (the `(vX)` merge on `main`) and pushed; v1.24.1 gets a GitHub
   release marked Latest. From now on every release is tagged at ship.
2. **The LTS policy, for users** (`README.md`, a short "Versions and support" section, and the
   CHANGELOG head):
   - an LTS line `1.24.x` takes **fixes only**: a script that does not behave as documented, a
     document that contradicts another, a broken reference, a selftest that cannot fail. No new
     rule, no new behavior, no new step;
   - fixes include a security weakness in a script or a rule (review Info-9);
   - it is supported until the next LTS is announced, and in any case until 2027-05-04 — 6 months
     after v1.24.1 (review L-5);
   - `main` carries new work as v1.25, v1.26, … — those are "current", not LTS;
   - training and adoption start from and pin a `v1.24.x` tag, not the template button, which
     copies `main` (review M-2); inside the line the CHANGELOG is the one on `lts/1.24`; leaving the
     line, a fix marked "also in v1.24.n" is skipped when the base holds it (review M-3).
3. **The LTS process, for maintainers** (`.anew-dev/README.md`): the branch `lts/1.24` starts at
   the v1.24.1 tag; a fix lands on `main` first through its own spec, then is cherry-picked onto
   `lts/1.24` by PR (`cherry-pick -x`), CI green, tagged `v1.24.<n+1>`, with the branch's own
   CHANGELOG entry and marker in place of `main`'s (review M-1); `main`'s entry is then marked
   "also in v1.24.<n+1>" (review M-3).
   A fix that does not apply cleanly is re-done on the branch, never forced. Nothing reaches
   `lts/1.24` that `main` does not already hold (G-2: the line never forks ahead).
4. **Release:** this change is v1.24.1 (CHANGELOG entry, `.anew-version`), the first patch of the
   line — it adds policy text only.
