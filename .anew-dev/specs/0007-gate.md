# Spec 0007 — scripts/gate: the human's decisions, written for them

- Status: Approved
- Mode: lite (ANEW's own development)
- Plan: `.anew-dev/plans/0007-plan.md`
- Self-critique: done (G-1–G-5 accepted, 2026-11-16)

## Intent
The human's four gates (spec approval, plan approval, triage, ship) are hand edits today. A
wrong `Approved by / on` form, a triage table with a misspelled verdict, or a ship that forgets
to move the spec is easy to make and is caught late, by doctor or by status. `scripts/gate`
writes each decision in exactly the form the human would write by hand, checks it before
writing, and commits it, so the decision is recorded once and correctly. It keeps no state of
its own and adds no new record: a team that never runs it follows the same process by hand. It
is also the write side a later screen calls, next to `scripts/status --json`.

Success means each gate is one command, its result reads the same to doctor and status as a
correct hand edit, and a malformed decision is refused before any file changes.

Deliberately not done:
- stopping an agent from running gate: the gate is a human decision whatever writes it, as with
  a hand edit today (Constraints);
- merging, pushing, tagging or opening a PR: ship writes the files and commits; the PR and the
  merge stay as they are (workflows/feature-development.md step 10);
- writing the scorecard, the amendments, or the backlog entries a triage refers to;
- an editor extension or a web screen; `.anew-dev/`.

## Requirements
1. **One command per gate**, each taking the spec number:
   - `approve-spec NNNN`: spec `Draft` → `Approved`;
   - `approve-plan NNNN`: the plan's `Status: Approved` and `Approved by / on: <name>, <date>`;
   - `triage NNNN --review|--verify` with zero or more findings, each a finding text, a verdict
     and a note: appends one round table to the plan's `## Triage`; zero findings writes a clean
     round (the heading with no rows, as the template allows);
   - `ship NNNN`: ticks every acceptance criterion not moved out and every Definition of Done
     box, sets `Status: Shipped`, moves the spec to `specs/done/`, and points the plan's `Spec:`
     line at the new path.
2. **The name is the git user, the date is today.** `<name>` is `git config user.name`; no
   option overrides it. A missing user name refuses.
3. **Only at its stage.** Each command reads the stage from `scripts/status` and refuses (exit 1,
   naming the stage it found) unless it is the stage that gate decides: ANALYZE for approve-spec;
   approve the plan for approve-plan; TRIAGE after a review, or the end of a VERIFY round, for
   triage; SHIP for ship. Two exceptions:
   - approve-plan on an approved plan is a re-approval: it writes a new value (the same day adds
     `(re-approved)`), the remedy status names for drift;
   - ship refuses while status shows a warning for that row (drift, old evidence, uncommitted
     approval).
4. **Checked before writing** (exit 2, no file changed): a verdict outside real / noise / defer /
   investigate; a noise verdict with an empty note; a defer whose note names no `B-<n>` present
   in the backlog; a finding text that is empty or holds a `|` or a line break.
5. **The triage heading** follows the template: `### Review round <n> — <name>, <date>` or
   `### VERIFY round <n> — <name>, <date>`, with `<n>` one more than the newest round of that
   kind, so status reads it.
6. **One commit per decision**, holding only the files gate wrote (a ship's move included), with
   a message naming the gate and the spec. Other staged or unstaged changes stay out of the
   commit and untouched. A target file with uncommitted edits is committed with them, and the
   output says so: the human approves the file as it is.
7. **Status reads an open investigate as unclear** (B-11): a newest round holding an
   `investigate` verdict reads "unclear: investigate open — <ids>" instead of SHIP or VERIFY.
8. **Same platforms as status** (POSIX sh, git, awk, sed, grep). Exit 0 on a written decision;
   1 on a refusal by stage or state; 2 on bad input or an unknown argument, with the usage.
   Without git, gate refuses: a decision needs its commit.
9. **Release:** v1.26 on `main`; nothing to `lts/1.24`.

## User experience
- **Flow:** the human reads the file, runs `./scripts/gate <gate> NNNN …`, and reads one line:
  what was written, to which file, and the commit. Then `scripts/status` shows the next stage.
- **States:**
  - **written**: `<gate> 0012: <what> — <file> @<sha>`;
  - **refused (stage)**: `0012 is at <stage>; <gate> decides <its stage>` (exit 1);
  - **refused (input)**: what is wrong, the usage, no file changed (exit 2);
  - **refused (state)**: no git, no user name, no such spec or plan, a status warning on ship
    (exit 1);
  - **with edits**: the written line plus "committed with your uncommitted edits to <file>".
- **Design reference:** the mockup https://claude.ai/artifact/E8Qy6Eo3zRcxap5RZWd63X (approval
  and triage screens) shows where these commands are meant to go; the terminal line is the design
  here. The mockup's approval screen is corrected separately (approve from the full file).
- **Accessibility:** plain text; every outcome is a word, not only an exit code.

## Constraints & out of scope
- The same shells as status (Linux, macOS, Windows Git Bash). Template users get it with v1.26.
- **An agent can run gate.** Nothing here tells a human from an agent; the same is true of the
  hand edit. The docs say that gate records a human's decision and that an agent never runs it
  on its own (docs/roles/README.md, The human's gates).
- Out of scope: role checks by git identity (G-3), the scorecard, merge/PR/tag, `.anew-dev/`,
  the extension.

## Acceptance criteria
- [ ] AC-1 — approve-spec on a Draft spec sets `Approved` and commits; on any other status it
  refuses (exit 1) and changes nothing.
- [ ] AC-2 — approve-plan writes `Status: Approved` and `Approved by / on: <git user>, <today>`;
  status then reads BUILD. On an approved plan it writes a new value (same day:
  `(re-approved)`) and status clears a drift warning. Without a plan, or with the spec not
  Approved, it refuses.
- [ ] AC-3 — triage appends a round table whose heading and number status reads; with no
  findings it writes a clean round, and status moves on (VERIFY after a review round, SHIP after
  a VERIFY round).
- [ ] AC-4 — each bad input of Requirement 4 exits 2 and leaves every file and the index
  unchanged.
- [ ] AC-5 — ship at SHIP ticks the criteria not moved out and the DoD, sets `Shipped`, moves
  the spec to `specs/done/`, fixes the plan's `Spec:` line, and doctor --strict stays green on
  the result. A struck criterion stays unticked; at any other stage, or with a status warning,
  ship refuses.
- [ ] AC-6 — each command makes exactly one commit holding only the files it wrote; an unrelated
  staged file stays staged and uncommitted; uncommitted edits in the target file go in and are
  named in the output.
- [ ] AC-7 — without git, without a git user name, or for an unknown spec, gate refuses (exit 1)
  and writes nothing; an unknown argument exits 2 with the usage.
- [ ] AC-8 — status reads a newest round with an `investigate` verdict as "unclear: investigate
  open"; the existing status scenarios stay green.
- [ ] AC-9 — `./scripts/selftest` and `./scripts/doctor --strict` are green; `docs/commands.md`
  documents gate; the CHANGELOG has a v1.26 entry and `.anew-version` is v1.26.

## Self-critique (approved 2026-11-16)
- **G-1 — approve-spec was not in the agreed three** (approve-plan, triage, ship). It is one
  status line, and a screen that approves plans but not specs is a gap. Recommendation: keep it.
- **G-2 — triage input on the command line.** A finding is passed as three arguments
  (`--finding "<text>" <verdict> "<note>"`, repeatable). Long texts are awkward to type, but the
  main caller is the human copying from the review report, or a later screen. Recommendation:
  accept; no interactive prompts (they break the screen and Git Bash pipes).
- **G-3 — role checks by git identity are dropped.** 0006 named "role checks for strict mode" for
  0007. With agents, every commit carries the human's git user, so "the builder approved their
  own plan" cannot be told from the history; a check would only look like protection.
  Recommendation: drop it, and say so in the docs.
- **G-4 — gate commits the target file whole.** A plan written by the Developer and not yet
  committed is committed by approve-plan with its content, so the approval commit is exactly the
  approved text (status's drift baseline). Recommendation: accept, and print it.
- **G-5 — B-11 rides here** (a status change in a gate spec). It is the gate's correctness: ship
  must never open on an open investigate. Recommendation: keep it in 0007.
